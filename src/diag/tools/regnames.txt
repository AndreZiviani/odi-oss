# Our names for the RTL9602C registers, read by tools/regmap-extract.py.
#
# The register table itself -- every address, width, array and port range,
# and every field bit range -- is read out of the stock firmware binary
# (librtk.so on the device). The binary carries no usable names for any of
# it, so every name in this project is ours: the ones below, chosen for what
# our code, scripts and docs actually touch, and a mechanical default for the
# rest.
#
# Defaults, for anything not listed here:
#   register   <BLOCK>_0x<address>, BLOCK from the block lines below, or R
#              for an address in no block: SW_0x023038, GPON_0x701010
#   field      F_<msb>_<lsb>, or F_<bit> for a one-bit field: F_15_8, F_5
#   reserved   RSVD_<msb>_<lsb> (the binary marks these with field id 0)
#
# Line formats:
#   block <first> <last> <PREFIX>
#   reg <address> <NAME> [<msb>:<lsb>=<FIELD> ...]
#
# A reg line names a register by its address (the base address, for an
# array) and a field by its bit range. The extractor refuses an address that
# is not in the table, a bit range that is not one of that register's
# fields, and a name used twice -- so a name here cannot silently drift off
# the thing it names when the base firmware changes.
#
# Where a name came from, when it is not obvious: the diag command whose
# handler touches the field (from the command tree), the rcS or network.sh
# step that writes it, or the odi_gpon/odi_switch driver's use of it. The
# kernel register headers (odi_gpon_hw.h, odi_switch_hw.h) use exactly
# these names; test/regnames_kernel_test.py holds them to this file.

block 0x000000 0x6fffff SW
block 0x700000 0x7fffff GPON
block 0xf00000 0xffffff PONQ

# ---- pin mux, host SerDes (rcS, etc/scripts/network.sh)
